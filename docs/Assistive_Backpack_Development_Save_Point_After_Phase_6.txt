PROJECT GOAL AND DEVELOPMENT APPROACH

Build and validate the backpack’s logical “brain” as ordinary C++
software before connecting hardware. Keep core logic independent of
Arduino pins, RFID libraries, LCDs, LEDs, buzzers, audio players, and
button hardware.

The core coordinates: - Item/tag definitions and inventory - Task
definitions and requirements - The backpack finite-state machine (FSM) -
Logical event generation for later UI/feedback consumers

The hardware/input layer should call core functions. The feedback/UI
layer should consume logical events. Do not place calls such as
digitalWrite(), lcd.print(), RFID reader operations, or audio-player
calls inside the core.

Development workflow: responsibility -> header/interface ->
implementation -> compile -> test -> review -> Git commit/push -> next
module

The user prefers educational, stepwise explanations with meaningful
batches of related steps, compile/test checkpoints, and enough
explanation to understand and maintain the code independently.

IMPORTANT DESIGN DECISIONS

1.  Hardware independence: the software core must run on desktop and
    later compile for the target Arduino environment without depending
    on hardware APIs.
2.  RFID tag ID identifies a physical tagged object; ItemType is the
    logical category. Tasks require ItemType values, not RFID IDs.
3.  One active task at a time in V1.
4.  Inventory is the single source of truth. TaskManager receives an
    Inventory reference rather than maintaining a duplicate inventory.
5.  Inventory operations and task definitions remain separate.
6.  A scan is not automatically an add/remove. One RFID reading cannot
    by itself reliably determine whether an item entered or left the
    bag. Direction detection belongs in the future input/hardware layer;
    it should call itemAdded(tagID) or itemRemoved(tagID) once it has
    determined intent.
7.  The core generates logical events. UI/feedback modules will
    interpret them.
8.  Fixed-size arrays and explicit counts are preferred for predictable
    memory use on an Arduino-class target.
9.  Prefer non-blocking timing (for example millis()-style scheduling)
    for future reminder/feedback behaviour instead of long delay()
    calls.

PHASE 4 — BACKPACK COORDINATOR AND FINITE-STATE MACHINE

The Backpack class coordinates Inventory and TaskManager. It owns a
TaskManager constructed with a reference to the existing Inventory. The
Backpack exposes a public registerTask(const Task&) forwarding method so
callers can register tasks without exposing its private TaskManager.

Main states: - IDLE - CHECKING_INVENTORY - ACQUIRING_ITEMS -
TASK_REMINDER

Expected flow: IDLE -> startTask() -> CHECKING_INVENTORY ->
ACQUIRING_ITEMS, if any required items are missing -> TASK_REMINDER,
once all requirements are present

If all requirements are already in inventory, checking can proceed
directly to TASK_REMINDER. TASK_REMINDER persists until stopTask() or
the task is otherwise ended. V1 does not need a separate TASK_COMPLETE
state.

Key functions include: - begin() - registerTask(const Task&) -
startTask(TaskType) - stopTask() - itemScanned(uint32_t tagID) -
itemAdded(uint32_t tagID) - itemRemoved(uint32_t tagID) - getState(),
getCurrentTask(), getCurrentRequiredItem() - isTaskActive(),
isTaskComplete()

Important behavioural details: - Backpack::startTask() rejects attempts
unless the Backpack state is IDLE. - TaskManager::startTask() also has a
defensive guard that rejects starting when taskActive is already true. -
checkInventory() reuses TaskManager::isTaskComplete() to choose between
TASK_REMINDER and ACQUIRING_ITEMS rather than duplicating completion
logic. - itemAdded(tagID) updates Inventory. If the Backpack is
currently in ACQUIRING_ITEMS, it rechecks inventory and can move to
TASK_REMINDER. - Calling inventory.addItem() directly changes inventory
but does not trigger Backpack FSM behaviour. Use backpack.itemAdded()
when the logical operation should also notify/update the Backpack
coordinator. - itemRemoved(tagID) updates inventory. Confirm whether
removal during an active task should also trigger a state recheck/event;
test this in later integration work rather than assuming it is already
handled. - isTaskActive() has been implemented using the Backpack state;
inspect the current code if state/task-manager activity ever appears
inconsistent.

PHASE 5 — EVENT SYSTEM

An EventGenerator was added and then changed from a single-last-event
holder to a fixed-size FIFO queue, because a single operation may
generate multiple events. The queue uses a configured maximum
(MAX_EVENTS in Config.h; check the current value in source).

The queue concept: - emit(event) adds to the queue and reports
success/failure - hasEvent() checks whether queued events exist -
getEvent() returns/removes the oldest event - clear() clears queued
events

Backpack exposes queue accessors: - hasEvent() - getEvent() -
clearEvents()

The exact EventType names/fields are defined in the repository’s
Events.h. Events discussed/used across the implementation include: -
TASK_STARTED - TASK_STOPPED - ITEM_REQUIRED - ITEM_ACQUIRED -
ITEM_NOT_REQUIRED - UNKNOWN_RFID - TASK_COMPLETE - TASK_REMINDER -
ITEM_ADDED - ITEM_REMOVED, if present in the current enum

Do not assume every listed event is emitted by every relevant function
yet. Inspect Events.h and Backpack.cpp before adding new event
behaviour. Phase 5 manual tests 1–7 passed. Queue maximum-capacity
overflow was not tested. If emit() fails because the queue is full,
consider how the caller should handle/report the dropped event during a
later robustness pass.

TaskManager also gained: bool isItemRequired(ItemType type) const;

It returns false when no task is active or the active task cannot be
found; otherwise it checks the active task’s requiredItems array.
Backpack exposes the corresponding query. This helps distinguish an item
required for the active task from an unrelated item.

PHASE 6 — RFID SCAN SIMULATION / INTEGRATION HOOK

Phase 6 added/updated Backpack::itemScanned(uint32_t tagID) to
distinguish registered and unregistered RFID tags. The user’s current
reported behaviour is:

-   Registered/known tag scanned: currently no event/action is emitted
    by the scan itself.
-   Unregistered/unknown tag scanned: emits UNKNOWN_RFID.
-   During an active task, adding a known item that is required for the
    task updates inventory and emits ITEM_ACQUIRED.
-   During an active task, scanning an unknown tag currently adds an
    ItemType::Unknown entry to inventory, emits ITEM_NOT_REQUIRED, and
    returns to normal operation.
-   Unknown tags can be stored with no assigned logical item type.
-   The user has tested both known and unknown tag scans/additions.

CAUTION: the exact behaviour above is a report of the latest testing,
not a guarantee that all scan/add/remove flows are conceptually final.
In particular, scan, registration, inventory addition, and direction
detection are separate operations. Review the actual implementation
before refactoring. A future console should make those distinctions
explicit to prevent a scan from silently meaning “item entered the bag”.

Potential conceptual distinction: - RFID scan: reader detected tag ID. -
UNKNOWN_RFID: tag ID is not registered/mapped. - ITEM_ADDED: item is now
represented in inventory. - ITEM_ACQUIRED: item was added and satisfies
a requirement for the active task. - ITEM_NOT_REQUIRED: scanned/added
item is not a requirement for the active task, according to the
implemented event semantics. Ensure the final event semantics are
documented and consistent before hardware integration.

A teammate reported that #include <cstdint> (the user initially wrote
“cintsdt”) was unavailable in their Arduino environment while testing

Record this as an UNRESOLVED COMPATIBILITY REPORT, not yet a confirmed
defect: <cstdint> is a standard C++ header, but availability can depend
on the selected board core, compiler/toolchain, and how the code is
being compiled. Do not blindly replace it before reproducing the error.

During Phase 8: 1. Record the exact board model, Arduino IDE/CLI
version, selected board core and version, compiler error text, and the
file/line that fails. 2. Confirm whether the failing code is compiled as
C++ and whether the selected toolchain provides the standard header. 3.
Check whether the Arduino library is being built through the intended
Arduino library layout/build system rather than compiling a
header/source in isolation. 4. If the environment genuinely does not
support <cstdint>, choose a consistent, target-compatible integer type
strategy (for example, the platform’s supported fixed-width integer
header/types) and update all affected files together. Avoid mixing
incompatible declarations. 5. Rebuild both the desktop CMake version and
the Arduino version after any change so portability regressions are
caught. 6. Keep the core hardware-independent; do not add
Arduino-specific includes to general core headers just to work around
one compile error.
